## 3. 指摘の詳細

### R1. ゼロサイズの表示領域で変換更新が例外になる

**箇所:** [Device.ViewArea](../WpfCad2Lib.Wpf/Core/Device.cs#L43)、[行列生成と反転](../WpfCad2Lib.Wpf/Core/Device.cs#L148)、[View のサイズ変更](../WpfCad2Lib.Wpf/Core/View.xaml.cs#L134)。

```csharp
var device = new WpfCad2Lib.Wpf.Device();
device.ViewArea = new System.Windows.Rect(0, 0, 100, 0);
```

上記で `InvalidOperationException: 変換は可逆的ではありません。` を確認した。幅または高さが 0 だと表示倍率が 0 になり、特異行列に対して無条件に `Invert()` する。

View は実際のサイズをそのまま Device に渡しているため、レイアウト途中・極端な縮小等で 0 になった場合に例外が UI イベントから伝播する経路がある。ただし、現在の TestApp を手で縮小してこの状態にできるかは確認していない。

**修正案:** 表示領域が正の大きさになるまで行列更新を延期する等、ゼロ寸法をレイアウト上の一時状態として扱う。単に例外を握りつぶすのではなく、変換不能な間の入力の扱いも決める。

**必要なテスト:** 正常サイズ → 幅 0 / 高さ 0 → 正常サイズで、例外なく復帰し、往復座標変換が再び成立すること。

### R2. リサイズでパン位置・ズーム中心が失われる

**箇所:** [ViewArea の変更](../WpfCad2Lib.Wpf/Core/Device.cs#L43)、[ズーム・パン](../WpfCad2Lib.Wpf/Core/Device.cs#L119)、[行列の再構築](../WpfCad2Lib.Wpf/Core/Device.cs#L154)。

モデル領域・表示領域をともに 1000 × 1000 とし、`Pan(Direction.Left, 0.1)` の後に表示領域を 1200 × 1000 に変えると、モデル原点の表示位置は次のようになった。

```text
リサイズ前: (141.4213562373095, 0)
リサイズ後: (0, 0)
```

この条件では基準倍率は変わらないため、平行移動だけが失われたことを確認できる。パン・指定中心でのズームの補正を行列にだけ保持している一方、リサイズ時は倍率等から行列を作り直すことが原因。

コード内でも制約として説明されているが、普通のリサイズで閲覧中の位置が飛ぶため、表示機能の改善対象とする。過去に修正された「パン後の Home が効かない」問題とは別である。

**修正案:** 表示中心等を独立した状態として保持し、サイズ変更後も追跡するモデル位置を維持する。

**必要なテスト:** パン後と中心指定ズーム後の両方で、リサイズ前後に表示位置の意図しないリセットがないこと。Home のリセット動作は別に検証する。

### R3. 拡大するとドラッグ開始の画面上の閾値も大きくなる

**箇所:** [入力座標の取得](../WpfCad2Lib.Wpf/Core/MouseEventConverter.cs#L11)、[開始距離の判定](../WpfCad2Lib.Wpf/Core/MouseEventConverter.cs#L82)、[クリック時の処理](../WpfCad2Lib.Wpf/Core/Controller.cs#L43)。

MouseEventConverter は変換された Canvas からモデル座標を取得し、その座標で開始距離 10 を判定する。このため、画面上で必要な移動量は `10 × モデルから表示への倍率` DIP となる。Home と最大ズームでは、この画面上の閾値が 16 倍違う。

拡大した状態で短い線分・矩形を作ろうとしても、モデル上の移動距離が 10 未満ならクリックになる。作図コマンドはクリックで図形を追加しないため、細部を描こうとするほど作図できない。

これは座標系と判定式の静的確認による指摘であり、ズーム後の実マウス操作は行っていない。

**修正案:** クリック／ドラッグの分類は未変換の View 座標で判定し、図形に渡す位置は従来どおりモデル座標とする。

**必要なテスト:** 同じ画面上の移動量が倍率によらず同じ入力に分類され、作成された図形の座標はモデル座標で正しいこと。

### R4. 楕円の当たり判定が外接矩形と一致してしまう

**箇所:** [RectFigure の距離判定](../WpfCad2Lib.Wpf/Figures/Figures.cs#L94)、[EllipseFigure](../WpfCad2Lib.Wpf/Figures/Figures.cs#L153)、[矩形との距離](../WpfCad2Lib.Wpf/Utility/Geometry.cs#L230)。

外接矩形 `(0, 0)`–`(600, 600)` の円を作り、距離 40 の許容値で `IsNear()` を呼ぶと次の結果になった。

| 点 | 本来の位置 | 実際の結果 |
|---|---|---|
| 約 `(512.132, 512.132)` | 45 度方向の円周上 | `false` |
| `(600, 0)` | 円から離れた外接矩形の角 | `true` |

EllipseFigure が RectFigure の距離判定を継承しており、円周ではなく矩形の辺からの距離を返すためである。近似である旨の説明はあるが、この条件では選択許容距離を大幅に超える誤差になる。

許容値 40 は、モデル領域 1000 × 1000 に対する通常の NearDistance と同じであり、極端に小さい許容値を与えた場合だけの問題ではない。

**修正案:** 楕円の輪郭に対する距離または適切なストロークのヒットテストを実装する。

**必要なテスト:** 主軸端点、45 度方向、外接矩形の角、楕円の内外、幅・高さの異なる楕円。

### R5. WinForms でキャプチャー喪失後の移動が作図として処理される

**箇所:** [MainForm のイベント配線](../BezierWinForm/MainForm.cs#L29)、[Controller.OnMouseMove](../BezierWinForm/Controller.cs#L59)、[Framework 版の配線](../BezierWinForm.NETFramework/MainForm.cs#L29)、[Framework 版の移動処理](../BezierWinForm.NETFramework/Controller.cs#L60)。

押下 `(0, 0)` → 左ボタン付き移動 `(20, 0)` → `MouseCaptureChanged` → ボタンなし移動 `(80, 0)` のイベント列を .NET 10 のフォームに与えた。

```text
キャプチャー喪失前の通過点: 2 個
ボタンなし移動後の通過点:   3 個
Controller の作図中参照:    残存
Model の確定済み図形:       0 個
```

移動通知はボタン状態によらず Controller に転送され、Controller は作図中参照の有無だけで処理する。通常の MouseUp は処理するが、キャプチャー喪失・操作中断から待機状態へ戻る処理がない。

**通常の WinForms の自動キャプチャー自体がない、という指摘ではない。** 操作途中でキャプチャーを失い、対応する MouseUp が来なかった場合に備えていない点が問題である。Alt+Tab 等の実操作は未確認だが、喪失通知後に状態が残ることはイベント列で確認した。Framework 版は同じ実装を静的確認した。

**修正案:** 異常終了時に最後の有効な位置で確定するか取り消すかを決め、必ず作図状態を解放する。通常終了に続くキャプチャー喪失で二重確定しないようにする。

**必要なテスト:** ドラッグ中のキャプチャー喪失後、ボタンなしの移動で図形が変わらず、次の押下から正常に作図できること。

### R6. WPF 系の解放時閾値判定が HTML 版と不一致

**箇所:** [WPF の解放処理](../BezierWpf/MouseEventConverter.cs#L109)、[Framework 版](../BezierWpf.NETFramework/MouseEventConverter.cs#L114)、[CAD 版](../WpfCad2Lib.Wpf/Core/MouseEventConverter.cs#L98)。

```text
押下 (0, 0) → 移動通知なし → 解放 (30, 0)
押下 (0, 0) → 移動 (9, 0) → 解放 (30, 0)
```

.NET 10 WPF の変換器を Controller と線分コマンドにつないで実行したところ、どちらも通知は `Click` のみ、Canvas の子要素は 0 個だった。

開始距離を判定するのが移動処理だけで、解放処理は `isDragging` / `isStarted` の状態だけで分岐する。Framework 版と CAD 版にも同じ判定漏れがある。

この問題は [HTML 版の前回レビュー](2026-10-22-bezier-html-review.md) で修正されたが、WPF 系には残っている。実際にどの頻度でこのイベント列になるかは手動確認していない。

**修正案:** 解放位置でも開始距離を調べ、閾値以上なら開始・保留した移動・解放位置での移動・終了を順に通知する。終了だけの通知では、最初の移動で図形を作る設計と整合しない。

**必要なテスト:** 移動なし／保留点あり、閾値ちょうど／未満、図形の追加と終点、二重終了の防止。HTML 版と同じケースを、共通化せず各実装に適用する。

### R7. WPF 系のドラッグ通知先が途中で変わる

**箇所:** [WPF Controller](../BezierWpf/Controller.cs#L55)、[Framework 版](../BezierWpf.NETFramework/Controller.cs#L68)、[CAD Controller](../WpfCad2Lib.Wpf/Core/Controller.cs#L24)、[CAD の作図処理](../WpfCad2Lib.Wpf/Core/Command.cs#L75)。

.NET 10 WPF で次の公開 API 呼び出しを行った。

```text
線分 Command を設定
開始 (100, 100) → 移動 (120, 110)
矩形 Command に差し替え
移動 (140, 130) → 終了 (150, 140)
```

結果は図形 2 個で、線分は `(120, 110)` までの未完了状態のまま旧 Command に保持された。新しい矩形は開始通知を受けていないため、原点 `(0, 0)` から幅 150・高さ 140 の図形になった。

CAD 側も同じ通知先変更を行い、旧 Command が Canvas に追加した図形を終了時に Model へ登録できず、選択対象にならない図形が残る経路がある。

**API 上の不具合として扱う。** 現在のメニュー操作ではキャプチャー喪失により終了が先行し得るため、通常の UI 操作から同じ順序になるとは断定しない。

**修正案:** HTML 版の修正と同様に開始時の Command に終了まで委譲するか、差し替え前の確定・取消を契約として定義する。

**必要なテスト:** 同一モードの再選択・別モードへの変更、終了通知と参照解放、CAD の Canvas と Model の整合、次の操作の正常性。

### R8. 削除の Undo が元の順序を復元しない

**箇所:** [履歴の記録](../WpfCad2Lib.Wpf/Core/CadUndo.cs#L25)、[削除と復元](../WpfCad2Lib.Wpf/Core/CadUndo.cs#L162)、[末尾への再追加](../WpfCad2Lib.Wpf/Core/CadUndo.cs#L206)。

```text
CadData に A / B / C を追加
StartCommand() → B を削除 → Undo()
結果: A / C / B
```

図形の参照は戻るが順序は戻らないことを実行で確認した。履歴に削除元のインデックスを保存せず、Undo 時に `Add()` することが原因。同距離の選択候補を処理する順序等にも影響する。

現状の TestApp には Undo の UI 配線がなく、これを「現在のアプリの Undo ボタンが壊れている」とは扱わない。

**修正案:** 削除位置も記録して `Insert()` で復元する。複数削除では相互のインデックス変動も扱う。

**必要なテスト:** 中間要素の削除・複数削除・全削除とその Undo/Redo について、図形参照と順序が元に戻ること。

### R9. CadData.Update の更新対象と履歴の対象が異なる

**箇所:** [内部一覧と Update](../WpfCad2Lib.Wpf/Core/CadData.cs#L19)、[Update の実装](../WpfCad2Lib.Wpf/Core/CadData.cs#L70)、[Undo/Redo の対象](../WpfCad2Lib.Wpf/Core/CadData.cs#L140)、[更新履歴](../WpfCad2Lib.Wpf/Core/CadUndo.cs#L169)。

```text
CadData に older を追加
外部一覧 [older] を用意
StartCommand() → Update(外部一覧, older, newer)
```

次の結果を実行で確認した。

```text
戻り値:               true
CadData 内部の図形:   older のまま
外部一覧の図形:       newer に変更
```

引数の一覧が内部フィールドを隠し、書き換えるのは引数側だけだが、履歴を戻す処理は内部一覧を対象にする。内部一覧は通常の呼び出し側に公開されていないため、呼び出し側の工夫だけで整合させる契約になっていない。

Undo は内部にない newer を探すことになり、Debug のアサートに到達する経路がある。この追加の Undo 自体は今回の再現プログラムでは実行しておらず、コード上の確認である。現在、この API の呼び出し元はない。

**修正案:** 外部一覧の引数をなくして内部一覧を更新する等、Add/Remove と同じデータ所有の契約にする。外部一覧を更新する機能にしたい場合は、履歴も同じ一覧を対象に設計し直す必要がある。

**必要なテスト:** Update の成功直後、Undo 後、Redo 後で、本体を列挙した結果と図形参照・順序が正しいこと。

| CAD のゼロサイズ | `InvalidOperationException` |
| CAD のパン後リサイズ | 原点位置が約 `(141.421, 0)` → `(0, 0)` |
| CAD の削除 Undo | `A/B/C` → `A/C/B` |
| CAD の Update | 成功を返すが内部は older、外部だけ newer |
| CAD の楕円選択 | 円周上を見逃し、空の外接矩形の角を選択 |

この 8 処理の確認は、修正後のテスト成功を意味しない。.NET Framework 版は再ビルド・ソース照合までで、この一時プログラムによる実行は .NET 10 版を対象にした。

## 6. テスト・保守に関する推奨

1. **CAD の表示変換・当たり判定を優先してテストする。** R1〜R4 は表示・選択の基本機能に関係する。行列・距離判定の API テストと、サイズ変更からの経路を用意する。
2. **.NET 側にも入力シーケンスの回帰テストを追加する。** 現在の 41 件はスプラインとジオメトリー中心で、Controller / MouseEventConverter / CadData / Device / キャプチャー喪失のテストは見当たらない。HTML 版のテスト構成を参考にできるが、教材としての実装の分離は維持する。
3. **履歴 API と画面機能を区別する。** 現在の CadData の Undo/Redo はデータ専用で、Canvas を同期しないことが明記されている。StartCommand のアプリ側の呼び出しも未配線であり、今後 Undo を UI に公開する前に、グループ境界・図形順序・選択マーカー・画面要素を合わせて検証する。
4. **Win32 と .NET Framework 版の自動検証を拡充する。** 現在の幾何テストは .NET 10 側を参照しており、ビルド成功だけでは各版の動作同等性を保証しない。Win32 の整数丸めは、double 版の厳密な C² 連続性とは別の許容基準が必要になる。
5. **Windows CI で既存テストとビルドを継続実行する。** 現在のリポジトリに CI ワークフローは見当たらない。全体ビルドには v145 と Windows Desktop / .NET Framework の開発環境が必要なため、対応する runner を明示する。

今回、HTML 版と Win32 版に新たな確度の高い機能不具合は追加指摘していない。これは全入力・全ブラウザ・全環境での無欠陥を保証するものではない。意図的なコード重複、未実装と明記された編集機能、少数点の曲線を非表示にする仕様、純粋な命名・スタイルの好みは不具合に数えていない。
